# ファイルを新規作成したら整形を実行し、整形後の差分を確認してから完了とする

## 事象

`e2e/` へ新規の TypeScript ファイルを 7 本追加し、いずれもファイル冒頭にモジュール説明コメント
（そのファイルの役割と設計判断）を書いた。しかし `pnpm format`（oxfmt の `sortImports`）を実行すると、
冒頭コメントが型 import の下へ移動し、ファイルの先頭が `import type ...` 行になった。

```text
# 書いた形                     # 整形後
// 視覚ベースラインの採取。     import type { LogicalEntry } from "./locator-map/portable";
// ...                         // 視覚ベースラインの採取。
import { mkdir } from "...";   // ...
```

気づいたのが整形実行後だったため、7 ファイルを 3 周に分けて手作業で直した
（型 import の有無でパターンが違い、1 周では揃わなかった）。

## 根本原因

oxfmt の `sortImports` は**コメントを直後の import 文に付随させ、その import と一緒に並び替える**。
冒頭コメントを値 import の直前に書くと、その import が型グループの後ろへ並び替えられる際に
コメントも一緒に運ばれる。

なぜ気づかなかったか → ファイルを書き終えた時点の見た目で完成と判断し、整形を通した後の姿を
確認していなかった。
なぜ確認しなかったか → 整形は「自分が書いたものを壊さない」前提で扱っており、**整形器が自分の
レイアウトをどう作り替えるか**を新規ファイル追加時に確かめる工程が無かった ← 根本原因

同じ「既存ツールが追加物をどう扱うかを確認していない」という構図は
`.kaizen/2026-07-28-toolchain-scope-both-ways.md`（適用済み）と同型だが、あちらは**スコープ**
（対象に入るか）の話で、こちらは**スコープ内での変形**（対象に入った結果どう書き換えられるか）の話。
既存の学びは後者を扱っていない。

## 横断スコープ

同じ構図は他の自動書き換えツールにもある。`.editorconfig` を単一設定源とする `shfmt -w`、
`stage_fixed: true` で再ステージする lefthook の整形ジョブ、生成物を書き換える生成ツールが該当する。
いずれも「自分が書いた形」と「ツールを通した後の形」が違いうる。

## 提案

ファイルを新規作成したら、コミット前に整形を実行し、**整形後の差分を確認してから完了とする**。
自分が書いた形のまま残る前提で判断しない。整形器がレイアウトを作り替える箇所（import の並び替え、
コメントの付随、末尾カンマ等）は、追加時に一度実物で確かめる。

oxfmt を使う本プロジェクトでの具体形: ファイル冒頭のモジュール説明コメントは、**並び替え後に
先頭へ来る import**（型 import があればその先頭）の直前へ置く。

反映先: `docs/quality-checks.md` の「新しいファイル種別を追加するときの確認」節に、整形後の差分を
確認する工程と oxfmt の具体形を追記する。

## 適用（2026-07-28）

`docs/quality-checks.md` の「新しいファイル種別を追加するときの確認」節へ追記した。既存の
「両方向でスコープを確認する」規律と同じ節に置くのは、両者が「既存ツールが追加物をどう扱うかを
確認する」という同じ構図（スコープと変形）だから。

機構化はしていない。`format:check` は CI で失敗させるが、それが検出するのは「整形されていない」
ことであって「コメントの位置が意図とずれた」ことではない（整形後の形は常に整形済みなので通る）。
検出できる形が無いため、規律として記述した。
