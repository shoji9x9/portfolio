# 合否指標は、防ごうとしている失敗を検出できるか確かめてから使う

## 事象

Issue #52（狭い幅で横スクロールが発生する）の修正で、バッジ行の折り返しがアカウント
セクションに届いていなかった。アカウントバッジは折り返さない代わりに flex アイテムとして
縮み、485px で 5 件すべてが自然幅の 75%（390px で 51%、320px で 33%）まで横だけ潰れて
文字が読めない状態だった。

こちらは 320 / 360 / 390 / 485 / 768 / 1280px の 6 幅で
`documentElement.scrollWidth == clientWidth` と「viewport 右端を越える要素 0 件」を実測し、
「横スクロールは解消した」とユーザーへ報告していた。この指標では潰れが素通りする。
発覚はコードレビュー（`/code-review`）による。

## 根本原因

なぜ取りこぼしたか → 折り返し方針が `BadgeRow`（コンポーネント）と `App.tsx`（アカウント行の
独自 `flex items-center`）の 2 箇所にあり、コンポーネント側だけを直した。

なぜ 2 箇所目に気づかなかったか → 変更対象を「`折り返` というコメントの grep ヒット」で特定した。
コメントが書かれていたのは `BadgeRow` だけで、変更対象の構造（バッジ画像を横に並べる flex 行）の
全インスタンスを列挙していない。

なぜ検証で捕まらなかったか → 合否指標に `scrollWidth == clientWidth` を選んだが、器より広い
flex アイテムは横スクロールを作らずに縮むため、この指標は当の失敗モード（潰れ）を**原理的に**
検出できない。**指標が「防ごうとしている失敗」を実際に落とせるか確かめる工程が無かった**
← 根本原因

指標の盲点は、取りこぼしを隠しただけでなく、誤った完了報告そのものを生んだ。潰れを別指標
（描画幅／自然幅）で測り直して初めて、アカウント行だけでなく 320px でのカード内バッジの潰れ
（27 件・最小 59%）も可視化された。

## 横断スコープ

同じ構図は「その場で書く一時的な検証」全般にある。本リポジトリーのパリティスイートには
故障注入で差分器の強度を検証する工程（`e2e/parity/*/strength.spec.ts` と
`strength-results.json`）があり、「検出できることを確かめてから基準として使う」規律は
すでにプロジェクトの資産になっている。しかし作業中にアドホックに書く測定スクリプトには
その規律が効いていなかった。

既存の学び `2026-07-29-verify-under-observed-conditions.md`（applied）は「**測る条件**を
差分の観測条件から採る」という話で、今回は条件は網羅していた（6 幅）。**指標そのものが持つ
盲点**という別の軸なので、同じ節に並べて記述する。

## 提案

合否指標を決めたら、防ごうとしている失敗を意図的に作り、その指標が実際に落ちるか 1 回確かめる。
落ちない指標はその失敗モードには使えない。あわせて、変更対象は既存コメントや文言の grep では
なく、変えようとしている構造の全インスタンスで列挙する。

反映先: AGENTS.md の「調査と実験」節（既存の `verify-under-observed-conditions` と同じ節）。

## 適用（2026-08-04）

AGENTS.md「調査と実験」節へ 2 項目を追記した。`.agents/rules/` にしなかったのは既存の学びと
同じ理由で、この規律が特定パス配下の作業に閉じないため（検証スクリプトを書く／指標を選ぶ工程は
どのディレクトリーの作業でも起きる）。

機構化はしていない。「選んだ指標が当の失敗モードを検出できるか」を決定論的に検査する手段が
無いため。ただし本セッションでは `/code-review` が実際にこれを検出しており、
**レビュー役に実装意図ではなく差分だけを渡す**運用がこの種の盲点に効くことは既存の学びと
共通している。

コード側の再発防止として、折り返し方針を `BadgeRow` の 1 箇所に集約した（リンク付きバッジも
同じ器を通す）。方針が 2 箇所に分かれていたことが取りこぼしの直接の入口だったため。
