# 「変化なし」を結論にする前に、操作が成立したことを測る

## 事象

Issue #56（brace-expansion の脆弱性）の着手可否判定で、更新経路を一時ディレクトリーで実測した。
同じセッション中に「操作が実行されていないのに結果だけ読んだ」事故が 3 回起きた。

1. **`pnpm remove --lockfile-only` は lockfile を prune しない。** `references/pnpm-transitive-update.md`
   の手段2（親を remove して同一 range で add し直しサブツリーだけ再解決させる）を実行したつもりだったが、
   remove 後も `react-doctor` の参照が 4 件・`eslint` が 8 件・`minimatch` / `brace-expansion` が残っており、
   サブツリーは一度も再解決されていなかった。
2. **`pnpm remove --ignore-scripts` はフラグ非対応。** `Did you mean 'ignore-workspace'?` を出して
   remove 自体が失敗していた。それに気づかず後続の `pnpm add` と grep 結果だけを読んだ。
3. **一時ディレクトリーで `mise trust` を実行していなかった。** `mise ERROR ... are not trusted` で
   `node -e` が全滞していたのに、同じコマンド列の末尾で `=== exp dir ready ===` を表示して先へ進んだ。

1 と 2 はいずれも観測結果が「`brace-expansion@5.0.8` 据え置き」で、**経路が本当に効かない場合と区別が付かない**。
このまま「親を remove して add し直しても 5.0.9 には到達しない」と GitHub Issue へ実測として書く寸前だった。
実際にフラグを外して remove を成立させると 5.0.9 に到達し、結論は逆だった。

## 根本原因

なぜ誤結論しかけたか → 実験の**結果値**（`brace-expansion` のバージョン）だけを見て、
**操作が成立したか**を見なかった。

　なぜ操作の成立を見なかったか → 「変化なし」という観測が ①操作は成立したが効果が無かった
　②操作自体が実行されなかった の両方から出ることを意識していなかった。

　　なぜ意識できなかったか → **この非対称性が手順になかった**。陽性結果（変化した）なら操作は
　　成立している証拠が結果自体に含まれるが、陰性結果には含まれない。だから成立確認は陰性結果に対して
　　だけ追加で必要になる。既存の学び
　　[2026-08-03-green-check-is-not-evidence-of-action.md](2026-08-03-green-check-is-not-evidence-of-action.md)
　　は「success が作業実行の証拠にならない」を扱うが、あれは CI の条件付き skip が対象で、
　　**手元で書く一時的な実験の陰性結果**は射程外だった ← 根本原因

## 横断スコープ

同じ構図は、変更を加えて「効果が無かった」と判断するあらゆる場面に潜む。

- パッケージマネージャーの実験（フラグ非対応・`--lockfile-only` 等の副作用でコマンドが no-op になる）
- 一時ディレクトリー・サンドボックスでの再現実験（設定・信頼・依存が揃わずツールが起動していない）
- 設定値を変えて再測する切り分け（設定ファイルの書き換え先が実際に読まれているか）
- 「この修正では直らなかった」の判断（ビルド／再インストールを挟まず古い成果物を測っている）

なお本セッションでは、切り分けを 1 段深めた（ゲートを `minimumReleaseAge: 0` にする）ことで
`fast-uri` は「ゲート単独が障害」、`brace-expansion` は「ゲート以外にも障害あり」と分離でき、
これが誤結論の発見につながった。**陰性結果が出たら、操作の成立確認と条件の切り分けを両方行う。**

## 提案

「変化なし」を結論にする前に、操作が実際に成立したことを示す観測を別に取る。終了コード・stdout の
エラー文・中間状態（remove なら対象が lockfile から消えたか）を先に確かめる。陰性結果は、操作が
効かなかった場合と操作自体が実行されなかった場合の両方から出るため、結果値だけでは区別できない。

反映先は `AGENTS.md`「調査と実験」。既に「条件」（観測された条件そのもので測る）と「指標」
（防ごうとしている失敗を落とせるか確かめる）の 2 段があるので、3 段目として「操作の成立」を加える。
関連: [2026-08-03-green-check-is-not-evidence-of-action.md](2026-08-03-green-check-is-not-evidence-of-action.md)、
[2026-08-04-metric-must-detect-the-failure.md](2026-08-04-metric-must-detect-the-failure.md)、
[2026-08-03-measure-before-asserting.md](2026-08-03-measure-before-asserting.md)

追記する文面:

```markdown
条件と指標が正しくても、**その操作が実際に実行されていなければ**結論は誤る。「変化なし」を結論に
する前に、操作が成立したことを示す観測を別に取る。

- **陰性結果（変化なし・効果なし）には、操作の成立確認を必ず付ける。** 陽性結果なら操作が成立した
  証拠は結果自体に含まれるが、陰性結果には含まれない。この非対称性が見落としを生む
  （例: `pnpm remove --lockfile-only` は prune しないため親サブツリーの再解決が一度も走らないが、
  観測は「バージョン据え置き」で、経路が本当に効かない場合と区別が付かない）。
- 終了コード・stdout のエラー文・**中間状態**を確かめる（remove なら対象が lockfile から消えたか）。
  非対応フラグや未整備の前提でコマンドごと失敗していても、後続コマンドは成功したように見える。
- 陰性結果が出たら、操作の成立確認と条件の切り分けを**両方**行う。片方だけでは「効かない経路」と
  「走っていない経路」を分離できない。
```
