# 凍結・除外・基準化の運用方針は、ドキュメントへの記述ではなく実行経路への変更

## 事象

Issue #31 で「移行完了後は `.replace/parity/` の成果物（`metadata.json` の採取条件・
論理名一覧を含む）を凍結する」と「今後の回帰基準は `baseline-new`」を同じドキュメントに
書いたが、両立しない。`metadata.json` は `baseline-new.spec.ts` が実行時に読む入力
（`capture_conditions.browser` / `traits.elements`）で、凍結すると基準を採り直せない。
自分の検証（test / lint / パリティスイート）では出ず、`/code-review` が検出した。

実際、指摘を受けて実測すると新側採取は 2 つのゲートで落ちる状態だった——ブラウザー版の
不一致（記録 1.61.1 に対し実行中 1.62.0）と、論理名の完全一致判定（記録 136 件に対し
実際は 178 件）。どちらも「凍結」と宣言した `metadata.json` を更新しないと解けない。

## 根本原因

なぜ気づかなかったか → 凍結対象を「`.replace/parity/` 配下＝採取物」というディレクトリーの
見た目で決め、ファイル単位で「誰がいつ読むか」を確かめなかった。

なぜ見た目で決めたか → 運用方針の記述を「ドキュメントに書くこと」として扱い、コードの
実行経路に対する変更として扱わなかった。既存の検証はどれも方針文書を読まないので、
矛盾は機械的には検出されない。

なぜそう扱ったか → 「今後これは更新しない／これを基準にする」という方針は、実際には
**既存フローの入力の可変性を変える宣言**である、という捉え方がなかった ← 根本原因

## KEDB 照合

[`2026-08-03-early-exit-guard-changes-teardown.md`](2026-08-03-early-exit-guard-changes-teardown.md)
（applied）と同型。前回は「早期失敗の挿入は実行経路を 1 本増やす変更」、今回は「凍結は
入力の可変性を変える変更」。どちらも単体・文書の視点で捉えた変更が、実フローに効いていた。
偶然にも今回ぶつかったのは前回と同じガード（`assertBaselineBrowser`）である。
applied のため追記せず、恒久側（AGENTS.md）を直接強化する。

## 横断スコープ

同じセッションで `docs/quality-checks.md` に書いた「現行側の実行・再採取は行わず」も、
`browser-version.ts` の remedy（「現行側を採り直せ」）と矛盾していた（同一原因の第 2 例）。
一般には `.gitignore`・knip の ignore・oxfmt の `ignorePatterns`・CI の paths フィルターなど
「対象から外す」宣言全般に同じ構図。

## 提案

「今後これは更新しない／これを基準にする／これを対象外にする」という運用方針を書くときは、
対象ファイルを実行時に読むコードを grep で洗い、方針が既存の実行経路と両立するか確かめる。
凍結・除外・基準化はドキュメント上の言明ではなく、既存フローの入力の可変性を変える変更として
扱う。ディレクトリー単位ではなくファイル単位で「証跡か、実行時入力か」を分ける。

反映先: AGENTS.md「早期失敗を既存フローへ差し込むとき」の隣へ新節を追加。

## 適用（2026-08-04）

AGENTS.md の「ワークフロー」に「運用方針（凍結・除外・基準化）を決めるとき」節を新設した。
`.agents/rules/` にしなかったのは、この規律が特定パス配下に閉じないため（凍結・除外の宣言は
ドキュメント・設定・CI のいずれでも起きる）。前回の学びと同じ判断。

今回の実体側も併せて直した。凍結範囲を「現側の採取物（`baseline/` と
`strength-results.json`）だけ」へ狭め、`metadata.json` は新側採取の実行時入力として更新可能に
する旨を `.replace/features.md` へ明記。`browser-version.ts` の新側 remedy から「現行側を
採り直す」前提を外し、新側で閉じる手順へ変えた。

機構化（矛盾の決定論的な検出）はできていない。方針文書と実行経路の整合を機械的に検査する
手段が今のところ無いため、規律として置く。
