# 早期失敗を既存フローへ差し込む変更は、失敗経路を実フローで流して後始末を確認する

## 事象

ベースライン採取ブラウザーの陳腐化ガード（Issue #44）を `strength.spec.ts` の `beforeAll` に
入れた結果、ガード発火時にテストが 1 件も走らないまま `afterAll` が実行され、
`strength-results.json` を空配列 `[]` で上書きする欠陥を持ち込んだ。
**ガードが守ろうとした証跡を、ガード自身が壊す。** 自分の検証では見つからず、
`/code-review` が検出した（static-page / lapras の 2 箇所）。

## 根本原因

なぜ気づかなかったか → ガードの失敗経路を、実スペックではなく一時 probe スペック
（`assertBaselineBrowser` を直接呼ぶだけ）で確認したため。実スペックで流したのは
一致ケース（成功経路）だけだった。

なぜ probe で足りると判断したか → 検証対象を「新しく書いたロジックが正しく落ちるか」に
設定していたため。落ちること自体は probe で完全に確認できてしまう。

なぜそう設定したか → **早期失敗の挿入は「新しいロジックの追加」ではなく「既存フローの
実行経路を 1 本増やす」変更だ、という捉え方をしていなかった** ← 根本原因。
新経路（テストが 1 件も走らない）で既存の後始末が何をするかは、新ロジック単体では
原理的に観測できない。

補強する証拠: 同セッションで `-g` により 1 件だけ実行したとき `strength-results.json` が
1 件分に化け、2 回とも `git checkout --` で戻していた。「実行集合が変わると `afterAll` の
書き出しが証跡を壊す」を目の当たりにしながら、実行集合が空になる同型の事象へ一般化しなかった。

## 横断スコープ

同じ変更で `lapras/baseline-new.spec.ts` は `rm(outputDirectory)` を持つ。ガードを `rm` より
前に置いたため無事だったが、順序が逆なら同種の破壊が起きた。1 箇所の見落としではなく
「早期失敗の挿入位置と後始末の関係」という構図。`e2e/` 配下の `afterAll` は今回の 2 箇所のみ
（grep 確認済み）。一般には `finally` / `trap` / CI の `always()` / cleanup フックに同じ構図。

## 提案

早期失敗するガードや前提チェックを既存フローへ差し込むときは、失敗経路も実フローで実行し、
後始末（`afterAll` / `finally` / `always` / cleanup）が成果物に何をするか確認する。
「単体で正しく落ちる」ことの確認は、フローに組み込んだときの安全性の証拠にならない。

反映先: AGENTS.md「調査と実験」の隣に規律として追記。
機構側は既に決定論的に塞いだ（`afterAll` で `results` が空なら書き出さない）。

## 適用（2026-08-03）

AGENTS.md の「ワークフロー」に「早期失敗を既存フローへ差し込むとき」節を新設した。
`.agents/rules/` にしなかったのは、この規律が特定パス配下に閉じないため（早期失敗の挿入は
スペック・スクリプト・CI ワークフローのいずれでも起きる。rule は `paths` にマッチした
ファイルを編集するときだけロードされる仕組みで、`**` にしても常時ロードされない）。

機構化は本件については完了している。`strength.spec.ts` 2 ファイルの `afterAll` に
「`results` が空なら書き出さない」を入れ、改竄した metadata でガードを故意に落として
`strength-results.json` が md5 一致のまま無傷であることを実測した。
ただし「早期失敗の追加時に後始末を確認する」こと自体を決定論的に検査する手段は無い。
実際に検出したのは `/code-review` の敵対的レビューで、
[[2026-07-29-verify-under-observed-conditions]] と同じくレビュー運用がこの種の誤りに効いている。
