# 実際の出来事を間接証拠に使うときは、その出来事が走った条件で測る

## 事象

Issue #163 で pnpm 12 採用の根拠に「GitHub の Dependabot に
[dependabot-core#16376](https://github.com/dependabot/dependabot-core/pull/16376) が反映された」を挙げた。
推論は「11.28.4 は strict 既定で `pnpm update ... --lockfile-only --no-save -r` が失敗する → 2026-10-19 に
Dependabot の npm 更新 PR が 6 件（#157〜#162）作られた → strict を外す修正が反映済み」というもの。

だが失敗を測ったのは公開 1 日の knip 6.42.0 で、Dependabot は `cooldown`（`default-days: 7`）により
公開 7 日以上の版しか更新しない。その条件（公開 13 日の 6.40.0）では 11.28.4 も strict 既定のまま成功し、
推論は成り立たなかった。測定表には、すでに lockfile に入っている 6.41.0 への「更新」（何も変えない操作）も
成功例として載せていた。いずれも `/code-review --fix` が検出し、`docs/dependency-policy.md` を直した。

## 根本原因

1. なぜ誤ったか → 失敗を測った条件と、証拠に使った出来事（Dependabot の実ジョブ）の条件が違った
2. なぜ違いに気付かなかったか → 若い版を「失敗が出やすい代表値」として選び、出来事側の入力
   （cooldown が選ぶ版）を測定条件として取り出さなかった
3. なぜ取り出さなかったか → AGENTS.md「調査と実験」は「差分が観測された条件で測る」と書くが、
   自分の測定と実世界の出来事（PR 作成・ジョブ成功）を突き合わせて推論する場面を明示していない ← 根本原因

KEDB: [[2026-07-29-verify-under-observed-conditions]]（applied）の再発。applied ファイルへは追記せず、
本ファイルで記録する。無変化の操作を成功例として載せた点は、同節の「陰性結果には操作の成立確認を付ける」
と同じ構図（陽性に見える結果でも、中間状態が変わっていなければ操作は成立していない）。

横断スコープ: 「CI が green だった」「Dependabot が PR を作った」「デプロイが通った」を根拠に
外部システムの状態を推論する場面全般。いずれも外部側の入力（cooldown・paths フィルター・キャッシュ）を
自分の測定条件と照合する必要がある。

## 提案

実際に起きた出来事（PR が作られた・ジョブが通った）を間接証拠に使うときは、その出来事が実行された条件
（入力・設定・選ばれる版）を列挙し、自分の測定がその条件で行われたかを確かめてから結論する。

反映先: AGENTS.md「調査と実験」へ 1 項目追記する（例: Dependabot は cooldown で公開 7 日以上の版だけを
扱うので、公開直後の版での測定は Dependabot の成否の根拠にならない）。

## 再発（2026-10-20、Issue #167）

Dependabot 実ジョブのログで `pnpm --filter . peers check` が exit 1 になっていた。pnpm 12 採用の直後だったので、
「12 系で新たに通るようになった経路」と推測し、測らないまま Issue #167 の本文に書いた。

手元で再現すると、11.28.4（マージ前の main 07418e7）でも同じ exit 1 が出た。12 系固有ではない。
11 系の朝のジョブで走らなかったのは、vitest 5.0.4 が公開 7 日未満で cooldown に外されていたからだった。
`/code-review --fix` は、文書に残った同じ型の言い切り 2 件（理由を書かない断定、ログ 1 行からの一般化）も検出した。

根本原因は前回と同じ。出来事（ジョブの中で、ある経路が走ったこと）の条件、つまり「どの版が更新対象に入ったか」を
取り出さず、直前の変更（pnpm の版）と結び付けた。

追加の提案: 外部ジョブのログに新しい挙動が見えたら、原因を書く前に、変更前の版でも同じ入力で再現するかを
1 回測る（変更前後の対照実験）。

## 再発（2026-10-22、Issue #169）

「`mise.toml` に完全なバージョンを書けば `minimum_release_age` は効かない」を、手元の mise 2026.5.16 だけで
測って `docs/dependency-policy.md` に「設定を変える必要はない」と断定した。
実際にこの設定を読んで install するのは CI で、mise-action が版を固定せずに解決する mise だった。
`ci.yml` の mise.lock 検査コメントには「CI の mise は未固定の最新。挙動が変わったと疑うときはその版で取り直す」と
明記されていたのに参照しなかった。`/code-review --fix` が検出し、手元で同日時点の最新 mise 2026.10.17 を
隔離して再測定した（結果は同じく成功）。同じ文書内の「更新候補を探すときにも効く」も実測なしの断定だった。

さらに、その 2026.10.17 も CI の版ではなかった。PR #170 の CI 実ジョブのログ（run 39694544633）では、
mise-action が mise 本体にも 24 時間の待機期間をかけて **2026.10.15** を選び、`mise install --locked` で
`node@26.12.1` を導入していた。「最新 = CI の版」という推測がもう 1 段残っており、docs と PR 本文に
「CI と同じ条件で確かめた」と書いた記述を、実ジョブのログに基づく記録へ直した。

根本原因は前回と同じ系統。断定の対象（CI での install の成否）が実行される条件（どの mise の版か）を
取り出さず、手元で測れる版を代表値にした。

追加の提案: ツールの挙動を断定する前に、そのツールを**実際に動かす実行系ごとの版**（手元・CI・Dependabot）を
列挙する。版が固定されていない実行系があれば、その実行系が解決する版で測るか、測った版を併記して
「版が変われば取り直す」条件を書く。
