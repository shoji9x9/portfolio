# 提案する修正の検証ケースは、観測した失敗だけでなく提案自体が作る失敗からも起こす

## 事象

kaizen v1.36.3 のコミット前ゲートが読み取り専用の git コマンドを誤ブロックする回帰を見つけ、
上流（shoji9x9/skills #202）へ修正案付きで報告した。修正案は「値を別引数として取る git の
グローバルオプションだけに引数消費を許す」形で、許容リストに 9 個を挙げた。

14 ケースの検証表で pass 14 / fail 0 を確認し、「真陽性を 1 件も落とさずに偽陽性 4 件が
解消」と Issue に書いた。上流の修正（PR #203）はこのリストから `--exec-path` を外していた。
`--exec-path` は値なしで呼ぶと exec-path を出力して即終了し、**次の引数を消費しない**
（実測: `git --exec-path version` は `/usr/lib/git-core` を出力し version を実行しない）。
リストに入れると `git --exec-path log commit` の `log` を引数として飲み、次の `commit` に
マッチして新たな偽陽性を作る。

後から `--exec-path` の 2 ケースを足して測り直すと、私の案は pass 16 / fail 2、
上流の v1.36.4 は pass 18 / fail 0 だった。

## 根本原因

なぜ穴が残ったか → 検証ケース表を、**観測された 4 つの偽陽性と既知の真陽性**からだけ作った。
提案した許容リスト自体が新しい偽陽性を作り得ることを、ケースとして 1 件も起こしていない。

なぜ起こさなかったか → 許容リストを「git のグローバルオプションのうち値を取るもの」という
一般知識と SYNOPSIS の書式（`--exec-path[=<path>]`）からの類推で作り、要素ごとに
「本当に次の引数を消費するか」を測らなかった。リストを測っていないので、リストの誤りを
落とすケースも思い付かない。

なぜ測らなかったか → 既存規律（AGENTS.md「調査と実験」）の「合否指標は、防ごうとしている失敗を
実際に落とせるか 1 回確かめてから使う」は、射程が**自分が観測した失敗モード**に閉じている。
**修正案そのものが新たに導入する失敗モード**（列挙の過剰包含・取りこぼし）が文面の射程外だった
← 根本原因

KEDB 照合: [[2026-08-04-metric-must-detect-the-failure]]（applied）と同型。あちらは
「指標が当の失敗を落とせるか」、本件は「ケース集合が**提案側**の失敗を含むか」。
[[2026-08-03-measure-before-asserting]]（applied）とも重なるが、あちらは「主張を測らずに書く」で、
本件は測ってはいる——測る対象の集合が偏っていた。いずれも applied のため追記せず恒久側を強化する。

## 横断スコープ

同じ構図は「リスト形の修正」全般にある。本リポジトリーにも要素の性質が効く列挙が複数ある:
`.github/license-policy.json` の `denyLicenses`（`scripts/check-licenses.ts` と
`scripts/generate-dependency-review-config.mjs` が読む）、`knip.ts` の `ignore` /
`ignoreBinaries` / `ignoreDependencies`、`.gitignore`、CI の paths フィルター。
AGENTS.md「運用方針（凍結・除外・基準化）を決めるとき」節は**除外の宣言**を既に扱っているが、
そこでの関心は「実行時入力を凍結していないか」であり、**列挙の要素が主張どおりの性質を
持つか**は別軸。

## 提案

修正案を検証するケース表は、観測された失敗に加えて、**その案が新たに作り得る失敗**を案の
構成要素ごとに 1 件ずつ起こして確かめる。特に許容・除外リストを提案するときは、要素ごとに
「本当にその性質を持つか」を一次情報で実測する（仕様書の書式からの類推は仮説）。
検証が全 pass でも、ケース集合が提案側に触れていなければ根拠になっていない。

反映先: AGENTS.md「調査と実験」節（既存の [[2026-08-04-metric-must-detect-the-failure]] と同じ節）。
